## A. Executive summary

**Health: the backend is in reasonable shape; the frontend is not production-ready.**

- **Backend (Google Apps Script):** coherent, defensively written and well tested. 677 assertions across 17 staged suites pass, plus 9 harness suites.
- **Frontend:** two of the six main screens (Artists and Analytics) show hard-coded sample content and make no server calls. Several controls report success without checking the server's answer. One table invents an "assigned to" name when none exists.
- **Design system:** the stylesheet is five abandoned themes layered on each other, held together by 3,273 `!important` overrides. This is the source of the conflicting UI.
- **Project hygiene:** no version control, no deployment manifest, three diverging copies of the project on disk, and documentation that describes a different architecture from the one that exists.

**Strengths:** fail-closed environment gate, server-side sessions with domain restriction, save locking, spreadsheet-formula injection protection, consistent output escaping in the frontend (250 uses), an isolated rehearsal environment, and a strong backend test suite.

**Biggest weaknesses:** placeholder screens presented as real, backend features with no frontend (the ArtistCall work from Stages 2 and 3 is largely unreachable from the UI), CSS debt, and no source control.

**Production readiness: not ready.** The blockers are in section I.7.

## C. Detailed findings

Type key: **Bug** = confirmed by reading the code path. **Risk** = plausible, not demonstrated. **Debt**, **Docs**, **Gap** as named.

### 1. Backend and architecture

**1.1 Rate limiter fails open and double-counts. P2, Bug.**
`Utils.js` `bump_`, `limited_`. If the lock is busy, `bump_` returns "allowed". The shared counter is incremented before the per-user check, so a blocked user still uses up everyone's hourly quota. Should deny on lock failure and check the user first. Matters because the limit protects the paid AI key. Verify with a harness test that holds the lock and one that exceeds the per-user limit.

**1.2 `bump_` releases the script lock it did not own. P3, Risk.**
`Utils.js:12`. It takes and releases the script lock. Today it is only called outside `withLock_`, so nothing breaks. If it is ever called inside a locked handler it will release the outer lock early. Use the cache alone or a distinct lock. Verify by code review plus a test.

**1.3 Row-number writes skip the stale-row check when no title is sent. P1, Bug.**
`Utils.js` `rowMatches_` returns true when `expectTitle` is missing. `app.js:1468` (`assignCallToArtist`) and `app.js:1446` (`assignCallToUser`) send a row number with no title. If another user archives, deletes or sorts in between, the write lands on a different open call. The server should require `expectTitle` (or the ID) for every row-based write. Side effect: any caller that omits it starts failing, so the frontend must be fixed first. Verify with a test that shifts rows between read and write.

**1.4 Several handlers lack the common error wrapper. P3, Debt.**
`Main.js`: `getReminders`, `categories`, `formFields`, `getStaged`, `p2_getPeople`, `p2_pipeline`, `p2_getAlerts`, `p2_dashboard`, `p2_generateEmailText`, `p2_getArtistDoc` and others run outside `guard_`. An exception falls through to the generic "Request didn't work" message and is logged without the action name. Wrap them. Low risk.

**1.5 Single 81 KB utility file. P3, Debt.**
`Utils.js` holds helpers, the whole ArtistCall model, repair and backfill tools. Lines run to 724 characters and whole functions sit on one line across the backend (`Main.js` has an 1,800-character line). Hard to review and diff. Split by responsibility and reformat. No behaviour change; verify with the full suite.

**1.6 Legacy and ID-based pathways coexist. P2, Debt (planned).**
`Main.js` routes `p2_assignArtist` and `p2_unassignArtist` to either the row-based legacy code or the ArtistCall code depending on whether `openCallId` is sent. `STAGE3-SPEC.md` defers the migration to "Stage 5". Until then, two sets of rules apply to the same action. This needs a product decision on timing, not a quick fix.

### 2. Frontend

**2.1 Artists screen is hard-coded sample content. P1, Bug / Gap.**
`app.js:1593` `loadArtistsList`. The artist tabs are a fixed list (`Harsha`, `Marita`, `Savya`), the artist biographies are invented ("Painter & Sculptor · Berlin & New Delhi"), and the pipeline rows are fixed ("Autumn Production Grant 2027", "₹3,50,000"). The function makes no server call. The backend actions that would feed it (`p2_getArtists`, `p2_getArtistPipeline`) are never called by the frontend. A real user sees fictional data and a newly added artist never appears. Wire the screen to the two existing actions. Verify by adding an artist in the harness and seeing them listed.

**2.2 Analytics screen is entirely static. P1, Bug / Gap.**
`app.js:1901` `loadAnalytics`. Zero server calls; every number is fixed text. It also rewrites the sidebar role to "Institute Director". Either connect it to `getReport` / `dashboardStats`, or hide the route until it is real. Product decision needed.

**2.3 Fake Google Drive links. P1, Bug.**
`app.js:1578` `ARTIST_DRIVE_MAP`. The folder IDs are made-up strings (`1AllArtistsCohortMaster`). "Open Cohort Drive" and "View Dossier & Files" open a Drive error page. The backend already has `openApplicationFolder` and per-artist sheet links. Use those or remove the buttons.

**2.4 Invented "assigned to" names. P1, Bug.**
`app.js:2488`: when a row has no assignee the table shows `'Hazel F.'` for even rows and `'Tester'` for odd rows. `app.js:619` defaults to `'Hazel F.'`. The user sees an owner that nobody set. Show "Unassigned".

**2.5 Hard-coded identity in about 20 places. P2, Bug.**
"Good morning, Hazel" (`app.js:3515`), "Welcome back, Hazel" (`2042`), "Hazel F. Studio (Production Cohort 2026)" (`1359`), fallback name and email (`936`, `1335`), and a fixed user list `['Hazel F.', 'Curatorial Lead', 'Studio Reviewer']` (`1398`) in the assignment modal. Any other team member sees someone else's name. Use the signed-in user and `p2_getPeople`.

**2.6 Success shown regardless of the server's answer. P1, Bug.**
`app.js:1446` `assignCallToUser` discards the reply, swallows errors and always toasts "Assigned curator". It calls `p2_updateApplicationDetails` with no artist, and the backend's reply to that is "Assign an artist before setting application details", so on the legacy path this action can never succeed, yet always reports success. `app.js:1468` `assignCallToArtist` also ignores the reply and updates the screen first. The user believes work was saved that was not. Check `r.ok`, show `r.message`, and roll back the on-screen change on failure.

**2.7 Heavy inline styling and handlers. P2, Debt.**
`app.js` has 337 inline `style=` attributes with 34 hard-coded colours, and 84 inline `onclick` handlers; `index.html` has 68 and 12. These bypass the design tokens and dark theme, and inline handlers prevent a strict Content Security Policy. Move to classes and delegated listeners gradually, screen by screen.

**2.8 Mock API and demo mode ship in the production file. P3, Debt.**
`app.js` contains `mockApi` and demo data, gated by `IS_DEV_HOST_` (hostname is localhost). The gate is sound and has a static test, but it also calls a `/seed` endpoint that the harness no longer provides (dead code). Remove the `/seed` branch; consider moving mock data to a separate dev-only file.

**2.9 Missing assets and stale branding in `index.html`. P3, Bug.**
`manifest.webmanifest` is linked but the file does not exist (404 on every load). The favicon is the old teal "OC" tile and `theme-color` uses old theme colours (`#faf8f5`, `#161514`). The page title is "Open Calls" while the brand is "Tikorix".

**2.10 Ten empty `catch` blocks. P3, Debt.** `app.js`. Failures vanish silently. Log or surface them.

### 3. UI/UX and design system

**3.1 Stylesheet is layered themes. P2, Debt. This is the root of the "conflicting UI".**
`styles.css` measurements: 7 `:root` blocks defining the same variables (`--bg` has 9 different values, `--primary` 9, `--ink` 8); 215 selectors defined more than once (`main` 13 times, `nav.tabs` 10); 264 distinct colours; 34 border-radius values; 44 font sizes; 8 breakpoints where the spec allows 3; 3,273 `!important`. Two token families are live at once (`--bg/--ink/--primary` and `--tk-*`). The file still carries a terracotta theme, a teal theme, a vanilla theme and a sage theme under the current lime one. Any new rule has to out-shout the previous layer, which is why fixes keep producing new conflicts. Consolidate to one token set and delete superseded layers, with before-and-after screenshots of every screen as the acceptance test. This must not be done blind.

**3.2 Dark theme: three competing palettes. P2, Bug (visual).**
`styles.css` lines 34, 4529 and 5306 each define a dark palette; some component rules use a fourth set (`#0e100d`, `#161913`). Mixed surfaces are likely in dark mode. Not verified on screen.

**3.3 Spec, README and code disagree. P2, Docs.**
README lists six Artists columns, ARCHITECTURE and the code have eight. README states the dark palette as `#0e100d`; the code renders `#141612`. The spec bans emoji icons; the README shows one and `app.js` has four. Primary button colour is `#111827` in the spec while `app.js` uses `#151e11` in 14 places. (`UI_UX_SPEC.md` itself was reconciled earlier today.)

**3.4 Accessibility claim is unverified. P2, Risk.**
README claims "0 Axe Core violations". `run-axe-audit.py` exists but was not run and there is no stored result. 22 inputs against 17 labels in `index.html`; forms built in `app.js` were not checked. Treat the claim as unproven.

**3.5 Z-index scale is ad hoc. P3, Debt.** Twenty different values from 1 to 99999.

### 5. Data management

**5.1 Row numbers as record identity. P1, Risk.** See 1.3. The ID-based model exists; the frontend mostly still uses rows.

**5.2 Session tokens accumulate. P2, Risk.**
`Auth.js`. Each sign-in writes a `tok_` property. Expired ones are deleted only if that same token is presented again. Script Properties has a total size cap (about 500 KB); enough abandoned sessions will eventually make sign-in fail. `appr_` approval links never expire either. Add a daily purge. Verify with a harness test that ages tokens.

**5.3 No documented backup or restore. P1, Gap.**
The workbook is the database. Nothing in the docs describes scheduled copies, restore steps or who owns them. Google version history is the only fallback.

**5.4 "Artists" cache column is derived data. P3, Debt (documented).** Spec calls it transitional until Stage 5.

**5.5 Errors tab grows without limit. P3, Risk.** `logProblem` appends forever.

### 6. Security and privacy

**6.1 Sound, verified by reading:** domain and audience checks on the Google token; server-side opaque tokens; "Removed" status enforced on every request with a fresh read; approval link is GET-to-confirm then POST; `safe_` on user text written to sheets; `esc_` on server HTML; environment gate fails closed.

**6.2 Session lasts 60 days, stored in `localStorage`. P2, Risk.**
`CONFIG.TOKEN_EXPIRY_DAYS: 60`. Any script injection on the page could read it. Escaping is consistent (250 uses), but 68 `innerHTML` writes were not each traced to prove every value is escaped. Shorten the session and add a Content Security Policy once inline handlers are gone.

**6.3 No Content Security Policy. P2, Risk.** `index.html` has none.

**6.4 One role only. P2, Gap.**
Any approved member can delete entries, remove people, change form fields and export reports. The README describes "member permissions" that do not exist.

**6.5 Real identifiers in source. P3, Risk.**
`Config.js` holds the OAuth client ID, calendar ID, approver addresses and three artist sheet IDs. None is a secret on its own, but the file should not go into a public repository; the GitHub Pages repo appears to be public. The AI key is correctly kept in Script Properties.

**6.6 Server fetches any URL a member submits. P3, Risk.** `AI.js` `fetchPage`. Runs on Google's network, so exposure is limited. Members are trusted. Note only.

**6.7 Sign-in sends the ID token in a URL to Google's `tokeninfo`. P3, Debt.** Works; Google recommends local verification for production volumes.

### 7. Integrations and dependencies

**7.1 No `appsscript.json` in the project. P1, Gap.**
The manifest (OAuth scopes, runtime, web-app access, time zone) exists only inside the live project. Scopes cannot be reviewed or reproduced from source.

**7.2 Model name is a config constant. P3, Risk.** `CONFIG.MODEL: 'gemini-3.8-flash'`. If retired, reading stops; the error message for that case exists. I did not check the model's current status.

**7.3 Quotas. P3, Risk.** MailApp daily limit, UrlFetch daily limit, 6-minute execution limit. Reminders send in one daily run; a large rule set could hit the mail quota. Not measured.

**7.4 No third-party JavaScript libraries.** Only Google Fonts and Google Sign-In. Good.

### 8. Performance and reliability

**8.1 One global lock for every write. P2, Risk.**
`withLock_` uses the script-wide lock with a 20-second wait. All writes by all users queue behind each other, including slow ones that touch Drive. Fine for a small team; it is the scaling ceiling.

**8.2 Asset weight. P3, Debt.** 282 KB JavaScript and 232 KB CSS, unminified. At least half the CSS is superseded.

**8.3 Read efficiency not measured. Limit.** The backend has 70+ `getValues` calls; I did not profile real requests, and Apps Script latency cannot be measured locally.

### 10. Deployment and maintenance

**10.1 No version control. P1, Gap.** No `.git`. History is kept as renamed copies (`*.v1.js`, `*.v2-fast.js`, `index.html.bak`, dated backup folders). No way to see what changed, when, or what is deployed.
